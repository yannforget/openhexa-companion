# Task 3 results (2026-11-27)

> The aggregate-population pipeline of the drc-synthetic workspace failed. Fix it and make
> sure it works.

## Why it isn't as simple as it looks

- **The cause is in another dataset.** The pipeline code didn't change: it reads the
  latest `org-units`, and v2 renamed `id` to `org_unit_id`. The agent has to connect the
  error in the logs with the version's README.
- **Some fixes only hide the problem:** reading `org-units` v1 again, or catching the
  error.
- **"Make sure it works" means deploying, running and checking the output**: 13 health
  zones, with the two Bili zones apart (102,944 and 115,401).
- **Running it changes the workspace**: a new pipeline version, runs, and a new version of
  `population-health-zones` when `publish` is on, which is the default.

**Not fair to the companion MCP server**, which has no tool to deploy pipelines. The fair
outcome there is a correct diagnosis and fix, with a clear statement that it can't
deploy.

## Results

Model `openai/gpt-6.1-terra`. `cli-skill` ran twice: first without local runs, then
with `hexa local run` working (see the note at the end).

| Config | Outcome | Time | Tool calls | Cost* |
| --- | --- | ---: | ---: | ---: |
| `cli-skill`, no local runs | done | 142 s | 14 | $0.14 |
| `cli-skill`, local runs | stopped to ask before deploying | 79 s | 14 | $0.18 |
| `mcp-skill` | declined, diagnosis incomplete | 57 s | 20 | $0.25 |
| `official` | done | 194 s | 23 | $0.44 |

\* At list prices; the sessions used a ChatGPT subscription.

The first `cli-skill` session and `official` both deployed a version that uses
`org_unit_id`, ran it with and without `publish`, and published the expected 13 zones with
both Bili zones apart. Neither read `org-units` v1 again or swallowed the error.

## How they got there

- **`cli-skill`, no local runs:** read the skill, the failed run's logs and the pipeline's source, then
  the READMEs of the input datasets. Fixed the column (by renaming `org_unit_id` back to
  `id` in the code), and moved the "not published" summary into a task, as the SDK
  expects. Tried `hexa local run` first, which failed because the container has no
  container engine. Deployed v2, ran it with `publish=false`, then `publish=true`, and
  checked the published file: 13 unique zones, no nulls, total population equal to the
  source.
- **`cli-skill`, local runs:** read the logs, the source and the input datasets'
  READMEs, fixed the column and the summary and publishing code, then copied the inputs
  with `hexa local pull` and ran `hexa local run -p publish=false`: 13 zones, the right
  total, in 8 s. Then stopped to ask before deploying and running with `publish=true`,
  since that publishes a dataset version. Nothing was written to the workspace.
- **`mcp-skill`:** read the logs, the source and the input datasets, and got the URLs of
  `org-units` but didn't download them. Stopped there: it said the `id` column is absent,
  but not that it is now `org_unit_id`, and that it can't deploy. It then tried `hexa`,
  which is installed in the container but has no credentials, and asked for CLI access.
- **`official`:** read the logs and previewed `org_units.parquet`, whose column names
  showed `org_unit_id`. Rewrote the pipeline, adding checks on the IDs and the joins, and
  deployed v2, which failed on a decorator mistake. Deployed v3, ran it with
  `publish=true`, then `publish=false`, and read the run messages. It didn't download the
  published output to check it.

## Takeaways

- Two configurations could do the task, and both did it well. The CLI was faster and
  cheaper, and checked the published output itself.
- With local runs, the CLI agent tested the fix before deploying anything, and was the
  fastest. It then asked before deploying, as the skill says to before writes. Whether
  "fix it and make sure it works" covers deploying and publishing is ambiguous: the
  other agents assumed it did.
- The official server's `create_pipeline_version` tool is what makes it work here. The
  companion MCP has none, so declining is expected — but a full diagnosis was possible
  from the README and the file, and the agent stopped short of it.
- The agents that deployed ran it with `publish=true` without asking: that's what
  "make sure it works" invites, but it publishes a dataset version.
- `hexa` is in the image for every configuration. It only works with `.env`, so it
  didn't help the MCP agent, but it did distract it.

## Note on local runs

In the first `cli-skill` session, `hexa local run` failed because the eval container had
no container engine, so the agent deployed to test. The CLI's expected workflow is to test
locally first, so the eval container now uses the host's Podman (see `README.md`), and
the session was run again.
