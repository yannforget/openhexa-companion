# Task 2 results (2026-11-27)

> In the drc-synthetic workspace, how many open health facilities per 10,000 people does
> each health zone have?

## Why it isn't as simple as it looks

- **The latest version is incomplete.** `health-facilities-snis` v3 has no Tshopo file
  and no `extraction.json`; its README says such a version must not be used. v2 is the
  right one.
- **Three datasets to join.** Facilities give a health zone; population is by health
  area, so it has to be summed by zone through `org-units`.
- **Two zones are named Bili**, in two provinces: grouping by name merges them.
- **Closed facilities** have a `closed_date` and must be left out.
- **There are decoys:** the legacy `formations-sanitaires` list, and the empty
  `population-health-zones` dataset.

Expected: 13 zones, from 0.34 (Gbadolite) to 1.29 (Lubunga), with Bili at 0.97
(Bas-Uele) and 0.87 (Nord-Ubangi). See `tasks.md`.

**Not quite fair to the official MCP server**: it can't read the README, which is where
the partial version is documented, nor analyse full files.

## Results

Model `openai/gpt-6.1-terra`, one session each.

| Config | Outcome | Time | Tool calls | Cost* |
| --- | --- | ---: | ---: | ---: |
| `cli-skill` | done | 74 s | 12 | $0.17 |
| `mcp-skill` | done | 213 s | 40 | $0.64 |
| `official` | wrong, unrequested writes | 152 s | 26 | $0.31 |

\* At list prices; the sessions used a ChatGPT subscription.

`cli-skill` and `mcp-skill` give exactly the expected values, with both Bili zones apart,
and say why they used v2 rather than v3. `official` used v3: Tshopo is "not available",
and Buta and Gbadolite are slightly too high (0.39 and 0.37) because v3 added two
facilities there.

## How they got there

- **`cli-skill`:** saw that v3 is the latest, read its README, listed the versions, then
  checked v2's files and README. Downloaded v2, `worldpop-health-areas` and `org-units`
  and computed in one script. Two failed commands while finding the right `hexa`
  subcommand.
- **`mcp-skill`:** started with v3 too, read its README, then fetched v2. Same result,
  but slow: `get_dataset_file_url` returns one signed URL per file, about 900 characters
  long, and the model has to copy each one into a `curl` command. The 11 URLs it used
  cost about 5,400 output tokens and 110 s of the 213 s. Tools themselves took almost no
  time: nearly all of it was the model writing.
- **`official`:** couldn't preview the README, so never saw the warning. Deployed a
  pipeline reading the latest version of each dataset; the first run failed, the agent
  deployed a second version, and read the result from the run's messages. It noted that
  Tshopo's file was missing but didn't look for the reason in other versions. The
  pipeline was left in the workspace (deleted after the session).

## Takeaways

- The task separates the configurations on correctness: only the configurations that
  can read the README found the partial version.
- Both companion configurations read the README of v3 before computing, which is what
  led them to v2. Neither was caught by Bili, closed facilities or the decoys.
- The companion MCP is slow when many files are involved, because the model copies each
  long signed URL by hand: almost 4 minutes, three times the CLI, and the most expensive
  configuration here. A variable wouldn't help, since each URL is typed only once; fewer
  or shorter URLs would.
- The official server again deployed and ran code in the workspace to answer a
  read-only question, and left it there.
